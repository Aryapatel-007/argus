# Phase E measurements

## First profiler run (2026-11-14, `scripts/profile_models.py`, repeats=2)

Full table: `notes/model-profiles.md` (regenerated by every profiler run).
Raw rows: `model_profiles`, `co_residency` in data/argus.db.

### What it says about routing

- **phi4-mini is the fast lane:** 2.9s cold, fully on GPU, ~81 tok/s.
  qwen3.5:9b is the slow one: 3.9s cold, 71% on GPU, ~25 tok/s (consistent
  with Sprint 0's 70/30 split and 19-24 tok/s). llama3.1:8b fully on GPU at
  ~51 tok/s. gemma4:e4b only 32% on GPU, 8.5s cold, ~33 tok/s.
- **No two chat models are co-resident except gemma4:e4b + phi4-mini**
  (gemma4 keeps most of itself on the CPU). Every other chat-model change is a
  swap. This is the scheduling problem ARGUS_BUILD 6.2 describes.
- **The fixtures saturate.** Most node types scored 1.0 for every model on
  this small set, so the priors barely separate the models on quality and the
  router will choose mostly on latency and swap cost. Exceptions:
  entity_match (qwen and phi4 0.67, llama and gemma 1.0) and write_fact
  (qwen and phi4 0.5, llama and gemma 0.0: they returned unchanged items too
  or scored importance differently). Phase F's eval harness adds harder
  scenarios; the bandit is what is meant to separate them in production.

### Two findings that looked like contradictions

1. **Co-residency is order-dependent.** Loading nomic-embed-text then
   qwen3.5:9b left only qwen loaded (Ollama evicted nomic to give qwen more
   VRAM). Sprint 2 Step 0 loaded qwen then nomic and both stayed. Both are
   true. The profiler now measures both orders and records a pair as
   co-resident only if both orders keep both. Practical effect: an embedding
   call after a qwen call is cheap (nomic loads beside qwen); a qwen call
   right after an embedding may cost a nomic reload later (~0.3GB, cheap).
2. **`think="low"` on qwen3.5:9b still thinks.** 1049 eval tokens for "low"
   vs 1348 for `think=True` on the same one-sentence prompt; the answers were
   near-identical but not byte-identical, so the profiler's strict
   "identical output" metric recorded 0. Sprint 1 recorded byte-identical
   output. The settled conclusion is unchanged: "low" is not a usable middle
   setting (over 1000 reasoning tokens for one sentence), and every call uses
   `think=False`. The metric is kept but should be read as "levels behave
   differently in output", not "low is cheap".

## Co-residency re-measured with Chromium running (Phase F step 3, 2026-11-14)

`python scripts/profile_models.py --coresidency-only --with-browser`, both
load orders per pair, headless Chromium open with a large page. Log:
`data/coresidency-browser.log`.

| pair | A then B | B then A | co-resident |
|---|---|---|---|
| qwen3.5:9b + nomic-embed-text | qwen then nomic: yes | nomic then qwen: no | no |
| llama3.1 + nomic-embed-text | yes | yes | **yes** |
| phi4-mini + nomic-embed-text | yes | yes | **yes** |
| gemma4:e4b + nomic-embed-text | gemma then nomic: yes | nomic then gemma: no | no |
| gemma4:e4b + phi4-mini | gemma then phi4: yes | phi4 then gemma: no | no (was yes without the browser) |
| every other chat pair | no | no | no |

Reading it:
- With a browser running, the only pairs safe in both orders are a small or
  mid chat model plus the embedder. gemma4 + phi4-mini lost its co-residency
  once Chromium took its share of memory: the browser does change the
  answer, which is why the directive asked for this re-measurement.
- qwen3.5:9b + nomic is order-dependent exactly as found before: an embed
  after qwen is free, qwen after an embed evicts nomic. The memory server
  embeds during `recall`/`remember`, which run on the I/O lane between GPU
  calls, so a qwen-heavy run pays a small nomic reload (~0.3GB) now and then.
- The router reads `co_residency` (both-orders rule), so these numbers are
  what it now uses.
